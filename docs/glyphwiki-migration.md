# 生成字の明朝体化：GlyphWiki＋KAGEエンジンへの移行計画

この文書は、移行を引き継ぐ人に向けて、決定事項、調査結果、作業手順、未決事項をまとめたものです。記述は2026-09-25時点のものです。作業が終わったら、内容を spec.md・README・data/README.md に反映し、この文書は削除してください。

## 1. 目的と決定事項

生成字の字形を、今の一定幅の線から明朝体にします。

- 部品と字形のデータを、KanjiVG から [GlyphWiki](https://glyphwiki.org/) のダンプに切り替える。読みは今までどおり KANJIDIC2 を使う。
- 描画には KAGE エンジン（GPL v3）を Go に移植して使う。
- **ライセンス**：リポジトリは GPL v3 を受け入れる。オーナーは、将来 public にする前提で了承済み。現在は private で、ライセンスは未設定。
- 描画はサーバー側（Go）だけで行う。ブラウザに GPL のコードを配らない。
- 画面とOGPの文字は、すでに Noto Serif CJK JP に切り替えてある。この文書の対象は生成字の字形だけ。

## 2. 経緯

1. 画面とOGPの文字を明朝体（Noto Serif CJK JP）にした。生成字はフォントではなく、KanjiVG の中心線を一定幅の線で描いているので、変わらなかった。
2. KanjiVG の中心線から明朝風の輪郭を自作した（縦は太く横は細く、うろこ、払いの先細りなど）。筆画の種類をデータが持っていないので、形から推測するしかない。その結果が「いびつ」で却下された。
3. GlyphWiki の部品を組み合わせた架空の字を、KAGE エンジン（`@kurgm/kage-engine`）で描いて試した。部品を縮めても太さの強弱が崩れず、本物の明朝体の品質だった。このとき部品同士が重なったのは、試しに位置を手で雑に指定したためで、エンジンの問題ではない。
4. エンジンを自前で実装する案と、GPL の移植を受け入れる案を比べ、後者を選んだ。自前実装は、作業量が大きいこと、GlyphWiki のデータが KAGE の描画を前提に調整されていること、GPL を避けたと保証しにくいことが理由で見送った。

## 3. 調査結果

### 3.1 データのライセンス

ダンプに同梱の `LICENSE.txt` の全文は次のとおり。

> このデータファイルはフリー（自由な）ソフトウェアです。あらゆる改変の有無に関わらず、また商業的な利用であっても、自由に利用、複製、再配布することができますが、全て無保証とさせていただきます。

Wiki の「データ・記事のライセンス」にも同じ趣旨が書かれていて、著作者表示にも制限がない。KanjiVG（CC BY-SA 3.0）より条件が緩い。

### 3.2 ダンプ

- **入手先**：`https://glyphwiki.org/dump.tar.gz`（約110MB）。1日ごとに作り直される。
- **中身**：`dump_newest_only.txt`（約300MB、各グリフの最新版）と `dump_all_versions.txt`（約950MB、全版）。
- **行の形式**：`名前 | 関連字 | KAGEデータ`。最初の2行は見出しと区切り線。ファイル先頭には BOM がある。
- **手元の場所**：`.local/sources/glyphwiki/` に展開済み。`.local/` は Git の管理外。
- **収録数**：2026-09-24版で2,154,633グリフ。

### 3.3 収録状況（今の辞書との比較）

- 今の辞書の字6,933字は、すべて `uXXXX` か `uXXXX-j` で収録されている。部品参照（`99`）を最後までたどれないグリフもなかった。
- `compose/radicals.go` の意符の字と、都市伝説枠の字（彁・妛・雲・龍）の計114字もすべて収録されている。
- 位置別の変形部品（接尾辞 `-01`〜`-06`）は4,604種ある。

### 3.4 KAGEデータ（観察した範囲）

仕様の原文は [GlyphWiki:KAGEデータ仕様](https://glyphwiki.org/wiki/GlyphWiki:KAGE%e3%83%87%e3%83%bc%e3%82%bf%e4%bb%95%e6%a7%98) にある。WebFetch では403で読めなかったので、以下は実データを見た範囲のまとめ。実装の前に原文とエンジンのソースで確かめること。

- **全体の形式**：1グリフが `$` 区切りの筆画の並びで、各筆画は `:` 区切りの数値。座標系は200×200。
- **先頭の数値（筆画の種類）**：
  - `1` 直線、`2` 曲線、`3` 折れ、`4` 乙線、`6` 複曲線、`7` 縦払い
  - `0` 特殊（変形の指定など）
  - `99` 部品参照
- **筆画の形**：2番目と3番目の数値が、始点と終点の形（うろこ、はね、止めなどのコード）。
- **部品参照（`99`）**：`99:?:?:x1:y1:x2:y2:部品名:…` の形で、部品の200×200の枠を矩形 `(x1,y1)-(x2,y2)` に伸縮して置く。部品名には `@版` が付くことがある。
- **例**：
  - `u6c35-01`（氵偏）：`2:7:8:33:20:59:28:69:41$2:7:8:12:68:38:75:49:89$…`
  - `u6c34`（水）：`99:0:0:0:0:200:200:u6c34-j`。親字の多くは、このように `-j`（日本の字形）への別名になっている。
- **位置別の変形部品の接尾辞**：`-01` 偏、`-02` 旁、`-03` 冠、`-04` 脚、`-05` 囲いの外、`-06` 囲いの中、`-07` 位置指定なしの部品、`-08` 縦長、`-09` 横長。
  - `-01`〜`-04` は、200の枠の中で本来の位置に寄せて描かれている（例：偏は枠の左半分）。
  - `-08`・`-09` は、約半分の大きさで枠の中央に描かれている。
- **KAGE の描き方**：骨格（制御点）を伸縮してから肉付けする。だから部品を縦横別々に伸縮しても、線の太さの強弱は保たれる。この性質が、今の「部品を枠に合わせて伸縮する」生成器と合う。

### 3.5 KAGE エンジン

| リポジトリ | 言語 | ライセンス | 備考 |
| --- | --- | --- | --- |
| [kamichikoichi/kage-engine](https://github.com/kamichikoichi/kage-engine) | JavaScript | GPL v3 | 公式（GlyphWiki の README が参照している） |
| [kurgm/kage-engine](https://github.com/kurgm/kage-engine) | TypeScript | GPL v3 | npm の `@kurgm/kage-engine`。試作ではこちらを使った |

試作で使った呼び出し方（Node、スクラッチ領域で実行。リポジトリには入れていない）：

```js
import { Kage, Polygons } from "@kurgm/kage-engine";
const kage = new Kage();
for (const [name, data] of Object.entries(buhin)) kage.kBuhin.push(name, data); // 参照先の部品を全部登録する
const p = new Polygons();
kage.makeGlyph(p, "target");
const svg = p.generateSVG(false);
```

組み合わせは、`99:0:0:0:0:200:200:u6c35-01$99:0:0:0:0:200:200:u9ed2-02`（氵偏＋黒の旁）のように、部品参照を並べるだけで作れる。

## 4. 今の実装との対応

| 今（KanjiVG） | 移行後（GlyphWiki） | 補足 |
| --- | --- | --- |
| `dict.Part.Paths []model.Stroke`（ベジェの中心線） | KAGE の筆画（種類、形コード、制御点） | 部品参照は構築時に展開して、筆画列として持つ |
| `Part.Bounds`（中心線の外接矩形） | 骨格の制御点の外接矩形 | 線幅ぶんの余白は描画結果で確かめる |
| `Part.Position`（KanjiVG の `position` 属性） | 接尾辞 `-01`〜`-06` と、親字の中での `99` の配置 | `whole` は `uXXXX-j` か `uXXXX` |
| 部品の抽出（KanjiVG の `element` グループ） | 親字（`uXXXX-j`）の `99` 参照 | 参照で組まれていない字（筆画を直接持つ字）は分解できない。部品は位置別の変形部品から取る |
| 読みの集計（部品を含む元の字の読み） | 同じ。「部品を含む字」を `99` 参照の逆引きで求める | `phon` 相当の情報はないので重み付けはなくなる |
| `data/component-overrides.json`（`kvg:` のID） | GlyphWiki のグリフ名で書き直す | 今は2件（囗、广）だけ |
| `compose/radicals.go` の `radicalChars`・`frameSpecs` | 字は同じでよい。部品の引き当ては位置別の変形部品 | 囲い・垂・繞の `inner` は、描画を見て調整し直す |
| `render.Fit`（中心線を伸縮） | 骨格の制御点を伸縮 | アフィン変換なので実装は単純 |
| `render.SVG`（`stroke` の線、太さ2.5） | KAGE の輪郭を塗りつぶした path | 1画ごとに1つの path にまとめると、画面のアニメーションに使える |
| `render.PNG` | `stroke-width` がない SVG は塗りつぶしで描く分岐がすでにある（`width == 0`） | そのまま使える見込み |
| 画面の書き順アニメーション（`stroke-dasharray`） | 塗りつぶしには効かない。1画ずつ現れる形などに作り直す | 保存済みの旧形式の SVG（線）とも両立させる |
| ライセンス表記 | KanjiVG（CC BY-SA 3.0）の表記を外し、GlyphWiki と GPL v3 を加える | KANJIDIC2（CC BY-SA 4.0）は読みに使うので残す |

## 5. 作業手順

各段階で、テストと実際の描画（見本画像）の両方を確かめること。

### 5.1 KAGE エンジンの移植（`internal/kage`）

1. `kurgm/kage-engine`（TypeScript）を元に、明朝体の描画（`Mincho`）だけを Go に移植する。ゴシック体（`Gothic`）はいらない。
2. ファイルの先頭に、元の著作権表示・GPL v3 の表示・改変した旨と日付を残す（GPL v3 第5条）。
3. **入出力**：
   - 入力：KAGE データ（参照を展開済みの筆画列、または部品辞書と名前）
   - 出力：1画ごとの多角形の列
4. **一致を確かめるテスト**：代表的な字と組み合わせ字（試作の8字など）を Node の `@kurgm/kage-engine` で描き、多角形の座標をテスト用のデータとして保存する。Go の出力が許容誤差の範囲で一致することを確かめる。Node はテストデータを作るときだけ使い、CI では使わない。

### 5.2 辞書の作り直し（`cmd/builddict`、`internal/dict`）

1. ダンプ（`dump_newest_only.txt`）を読み込む。tar.gz のまま読むか、展開したファイルを読むかは決めてよい。チェックサムを `data/sources.lock.json` に記録する。
2. 親字の範囲は、今と同じく KANJIDIC2 に読みがある字にする。`uXXXX-j` を優先し、なければ `uXXXX` を使う。
3. 部品を集める。
   - 位置別の変形部品（`-01`〜`-06`）を、今の left/right/top/bottom/enclosure などに写す。
   - `-07`〜`-09` と、親字の `99` 参照の配置から位置を推定するものは、後回しでよい。
4. 各部品の参照を展開して筆画列にし、外接矩形と画数を求める。
5. `99` 参照の逆引きで「部品 → 部品を含む字」を作り、読みベクトルと頻度を今と同じ方法で集計する。
6. overrides を GlyphWiki のグリフ名で書き直す。`verifySpecials`（都市伝説枠の素材の確認）は、そのまま使えるようにする。
7. 辞書の版（`Version`）は、ダンプのチェックサムから作る。gob の形式は今と同じ方針（マップはキー順のスライスにして、同じ入力から同じバイト列にする）。
8. 辞書のサイズと Lambda のコールドスタートを測る。今は gob で起動から応答まで約0.6秒（手元）。これが大きく悪化しないこと。

### 5.3 生成器（`internal/compose`）と描画（`internal/render`）

1. 配置（`layout`、`fitAspect`、`sideShare`）は、今の枠の計算をそのまま使う。伸縮の対象を、中心線から KAGE の骨格に替える。
2. 配置し終えた骨格を、`internal/kage` で一度に肉付けする。部品ごとに別々に肉付けしない。筆画同士の接続の調整が効かなくなるため。
3. 座標系の変換（今のキャンバス109 ↔ KAGE の200）を1か所にまとめる。
4. SVG は塗りつぶしの path で出力し、1画を1つの path にする。`aria-label` などは今と同じにする。
5. `GeneratorVersion` を2から3に上げる。`render.License` も書き換える。
6. `Strokes`（画数）は、展開後の筆画数で数える。

### 5.4 画面・OGP・文書

1. 画面の書き順アニメーションを、塗りつぶしの path に合わせて作り直す（1画ずつ現れる、など）。保存済みの旧形式（線の SVG）の結果もそのまま表示できること。
2. OGP画像が新しい形式の SVG で正しく描けることを確かめる。
3. 次の場所のライセンス表記を書き換える。
   - `web/src/main.tsx` のフッター
   - OGP画像の隅の表記（`render.PNG`）
   - `README.md`、`licenses/`、`spec.md` の第3.1節と第10章
   - KanjiVG の表記とファイル（`licenses/KanjiVG.txt`）は、KanjiVG 由来のデータがリポジトリから無くなってから外す。
4. リポジトリ直下に GPL v3 の `LICENSE` を置く。遅くとも public にする前までに。
5. spec.md の第3.1節（データソースと事前構築）、第3.6節（配置と表示）、data/README.md を、新しい構成で書き直す。

### 5.5 確認

- 全テスト（`go test -race ./...`、Web の `pnpm test`、E2E）
- 見本画像：レアリティ（N〜UR）ごと、囲い・垂・繞、同字重ね、都市伝説枠（彁・妛、タイト）
- `docker compose` で起動し、生成、共有ページ、OGP、保存済みの旧形式の結果を表示する
- デプロイ後に、コールドスタートの `Init Duration` と `Max Memory Used` を確認する

## 6. リスクと未決事項

- **ダンプの再現性**：ダンプは毎日作り直され、過去の版は取得できない。構築に使ったダンプそのものを保管する場所が要る（手元の `.local/sources/` だけでは失われる）。代わりに、`dump_all_versions.txt` から使った各グリフの版番号を記録する方法もある。
- **分解できない字**：参照（`99`）で組まれていない字（筆画を直接持つ字）は、部品に分解できない。今の KanjiVG の分解と比べて、部品の数と種類が減るかもしれない。構築の報告で件数を比べること。
- **位置の情報**：KanjiVG の `position` のような明示的な情報はない。接尾辞と `99` の配置からの推定になる。
- **保存済みの結果**：保存済みの生成字は、線の SVG のまま残る。新旧の見た目が混在することは、spec の第4.2節の方針（旧版の生成器は同梱しない）の範囲で受け入れる。
- **品質の調整**：部品を極端に縦横比を変えて伸縮した字や、画数の多い字（UR）で、線が潰れないか。KAGE の線の太さは固定なので、密な字では調整が要るかもしれない。
- **KAGE データ仕様の原文**：まだ確認していない（3.4節）。
- **public にするとき**：GPL v3 の `LICENSE` を置く。git の過去の履歴に AWS のアカウントIDと本番ドメインが残っているので、履歴から消すか、新しいリポジトリとして公開し直すかを決める。現在のファイルからは削除済みで、値は `.local/aws.md` にメモしてある。
